# QEMU Args Raw Edit v1

## 背景

`Sanaka` 当前的高级参数区已经从旧的大文本框，推进到了：

- 完整命令列表展示
- 部分内建参数双向同步
- custom 参数可增删

但继续沿着“尽量把每一行都解析回 UI 结构”的路线推进，会很快遇到新的复杂度问题：

- `-netdev` 往往不是简单字符串，而是一个不断拼接 extra 的结构
- 某些 `-device` 同时承担“UI 已知设备”和“用户临时实验设备”两种角色
- 如果每行都强行解析、校验、映射 UI，会让高级参数区再次退化成一套隐性规则引擎
- 用户修改后到底是“允许原样保留”还是“被系统重新规范化”，会越来越不透明

用户当前已经明确表达了更适合产品方向的原则：

- 高级参数区应允许直接编辑
- 不要过度检测、不要过度解析
- 语法问题先直接让 `QEMU` 报错

因此这一版 spec 的目标不是继续做“更聪明的解析器”，而是建立一套更克制、更稳定的规则：

- 保留少量真正有价值的 UI 同步
- 允许高级参数行原样编辑
- 对可关闭的内建项，提供明确删除语义
- 对无法映射回 UI 现有选项的值，UI 进入“自定义”态

## 目标

`v1` 目标是：

1. 高级参数列表中的行允许直接编辑原始字符串
2. 后端不对这类编辑做语法校验或智能纠错
3. 若参数语法错误，启动时直接让 `QEMU` 返回原始报错
4. 只有少量内建参数继续保留结构化同步
5. 只有“本来就可关闭”的内建项才允许删除
6. 删除内建项后，对应 UI 字段进入 `none` / `disabled`
7. 若内建值无法映射回 UI 现有枚举，UI 显示“自定义”

## 非目标

`v1` 不做以下事情：

1. 不实现“任意 QEMU 参数都能自动反推回 UI”
2. 不实现全量语法检查器
3. 不在高级参数区内模拟 `QEMU` 参数合法性
4. 不试图阻止用户写出错误参数
5. 不把所有内建项都做成可删除
6. 不引入“转为自定义 / 覆盖到 custom”这类用户难理解的内部概念

## 核心原则

### 1. 高级参数区优先是“原样命令编辑器”

它不是一个强结构化表单，也不是一个语法修复器。

对于允许原样编辑的行：

- 用户输入什么，就尽量保留什么
- 后端不主动重写、不主动规范化
- 启动失败时由 `QEMU` 自己给错误

### 2. 少解析，少魔法

后端可以保留少量必要解析，只用于：

- 识别哪些行属于“可关闭的内建项”
- 识别哪些行仍然绑定 UI 已知字段
- 识别哪些值会让 UI 进入“自定义”态

但不要继续扩大为：

- 任意参数智能识别
- 任意 `-device` 智能分拣
- 任意 `-netdev` 自动拆装

### 3. 删除能力只给“可关闭项”

删除不是“任意把某条命令删掉”。

删除只允许作用于：

- 本来就有 `none` / `disabled` / 关闭态的 UI 字段

例如：

- 声卡
- GPU
- 网络
- USB tablet
- 某些可为空的介质项

### 4. 不可关闭项不提供删除

以下这类项不应出现删除按钮：

- `-qmp`
- `-vnc`
- 控制器骨架，如 `ich9-ahci`
- 某些磁盘 / 光驱附着骨架
- 其他删掉就会让机器结构不完整的运行时参数

### 5. UI 可以显示“自定义”

如果用户修改了某个绑定 UI 的内建行，但值已经不属于 UI 现有选项：

- 后端保留该值
- UI 不强行回滚
- UI 对应字段显示“自定义”

这条规则比“禁止编辑”更符合高级参数区定位。

### 6. 简单直填参数不进入“自定义”

并不是所有 raw edit 都要把 UI 送进“自定义”态。

对于这类“直接填值”的简单参数：

- `-name`
- `-machine`
- `-m`
- `-smp`
- 以及其他本来就对应单个文本值或数值字段的参数

如果用户编辑后得到的仍是一个可直接写回字段的值，那么：

- 应直接回写到对应 UI 字段
- 不应把 UI 标成“自定义”

例如：

- `-m 2048` 改成 `-m 4096`

应当得到：

- `machine.system.memory_mib = 4096`
- UI 内存字段显示 `4096`

而不是：

- UI 显示“自定义”

“自定义”态只应用在这种情况：

- 参数仍绑定某个 UI 字段
- 但新值已经超出 UI 现有枚举或现有控件表达能力

例如：

- 某些 `-device`
- 某些 `-vga`
- 某些 `-netdev`

## 参数分层

这一版建议把高级参数行分成三类理解：

### A. Raw-bound controlled rows

特点：

- 来自内建命令生成
- 仍绑定某个 UI 字段
- 允许直接编辑原始字符串
- 后端只做最小映射

示例：

- `-name 新虚拟机`
- `-machine pc-q35-9.2`
- `-m 4096`
- `-smp 4`
- `-vga std`
- `-device intel-hda`
- `-netdev user,id=net0`

### B. Removable controlled rows

特点：

- 同样来自内建命令
- 绑定某个本来就可关闭的 UI 字段
- 除了可编辑外，还允许点击删除

删除后的语义不是“命令列表少一行”这么简单，而是：

- 回写 UI 字段为 `none` / `disabled`
- 然后重新生成命令

示例：

- 声卡设备行
- GPU 设备行
- 网络相关行
- USB tablet 行

### C. Custom rows

特点：

- 来自 `advanced.qemu_args`
- 原样保存
- 可新增、可编辑、可删除
- 不要求映射回 UI

## 用户交互规则

### 1. 原样编辑优先

对于进入 raw-edit 模式的参数行：

- 用户可以直接点开编辑整行
- 后端不主动对语法做拦截
- 保存后按当前字符串参与命令生成

### 2. 启动错误交给 QEMU

若用户把某行改坏，例如：

- `-netdev hostfwd=tcp...`
- `-device ???`
- `-machine ???`

则：

- 启动失败
- `QEMU` stderr 作为主要错误来源返回给用户

### 3. 可关闭项才出现垃圾桶

垃圾桶出现条件：

- `custom row`
- 或 `removable controlled row`

其余内建项不应显示删除按钮。

### 4. 删除可关闭项后的 UI 状态

建议映射：

- 声卡删除后：`system.sound_card = 'none'`
- GPU 删除后：`display.gpu = 'none'`
- 网络删除后：`network.enabled = false`，必要时 `network.card = 'none'`
- USB tablet 删除后：`peripherals.usb_tablet = false`

### 5. UI “自定义”态

若 raw edit 后值不在 UI 已知选项中：

- UI 下拉或字段显示“自定义”
- 不强行把用户值替换掉
- 重新打开高级参数列表时仍能看到原样值

## Runtime 语义

### 1. 运行时不做过度预检测

高级参数相关错误，优先让 `QEMU` 自己报。

Sanaka 只保留必要的前置错误：

- 缺失必需的二进制
- 缺失必需的路径文件
- 明显不完整的 machine 基础结构

但不要对高级参数字符串再增加一层复杂预检测器。

### 2. 完整命令展示要容忍 `none`

如果某个可关闭项被删除后进入：

- `gpu = 'none'`
- `sound_card = 'none'`
- `network.enabled = false`

则完整命令列表刷新时不应报“配置缺失”，而应正常展示删除后的命令结果。

### 3. 启动命令与展示命令尽量一致

高级参数区看到的完整命令，和实际启动命令应尽量使用同一套生成语义。

这样用户看到什么，就大致启动什么。

## 与旧 spec 的关系

这份 spec 不是完全否定：

- `speccodex/controlled-qemu-args-sync-v1/spec.md`

而是对它做收敛。

保留的部分：

- 完整命令展示
- 参数列表化
- UI 已知字段仍可同步
- custom 不生成新 UI 字段

收紧的部分：

- 不再追求“尽可能多的参数都被智能解析”
- 不再把高级参数区做成隐形结构修复器
- 更明确地承认 raw edit 与 QEMU 原始报错的价值

## 验证

完成后至少要验证：

1. 可关闭的内建项出现垃圾桶，删除后 UI 进入 `none` / `disabled`
2. 不可关闭的内建项不出现垃圾桶
3. 某些内建行允许直接改整行字符串
4. 改成 UI 未知值后，UI 显示“自定义”
5. 高级参数语法错误时，由 `QEMU` 返回原始启动错误
6. 完整命令展示在删除 `gpu` / `sound` / `network` 等项后不崩
7. `typecheck` 和相关 runtime / UI 测试通过
